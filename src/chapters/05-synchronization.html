Chương 05 — Trọng Tâm Thi Cuối Kỳ

ĐỒNG BỘ TIẾN TRÌNH (PROCESS SYNCHRONIZATION)

Race Condition $\rightarrow$ Vùng tranh chấp (Critical Section) $\rightarrow$ Thuật toán Peterson $\rightarrow$ Semaphore $\rightarrow$ Các bài toán kinh điển

🎯 Mục Tiêu Chương 5 (Trọng Tâm Cuối Kỳ UIT)

  • Hiểu bản chất Race Condition và tại sao truy xuất dữ liệu dùng chung bất đồng bộ lại gây ra sai sót.
  • Nắm vững 3 yêu cầu bắt buộc của giải pháp Vùng tranh chấp (Mutual Exclusion, Progress, Bounded Waiting).
  • Phân tích thuật toán Peterson và các chỉ thị phần cứng (TestAndSet, Swap).
  • Thạo kỹ năng sử dụng Semaphore để giải các bài toán đồng bộ thứ tự thực thi (Dependency DAG) và các bài toán kinh điển (Producer-Consumer, Readers-Writers).
  • Sửa lỗi Race Condition cho các chương trình thực tế chuẩn bài thi UIT.

1. NGUYÊN NHÂN RACE CONDITION VÀ BÀI TOÁN VÙNG TRANH CHẤP

A. Race Condition (Tranh chấp dữ liệu)

Khi nhiều tiến trình/thread truy xuất và thao tác trên dữ liệu dùng chung (Shared Data) một cách đồng thời, và kết quả cuối cùng phụ thuộc vào thứ tự thực thi ngẫu nhiên của các tiến trình, tình trạng đó gọi là Race Condition.

🔴 VÍ DỤ NGUYÊN TỬ VỀ RACE CONDITION

Giả sử 2 tiến trình $P_1$ và $P_2$ cùng thực hiện lệnh C counter++ trên biến toàn cục counter = 5:

Lệnh counter++ trong mã máy thực chất gồm 3 bước:

  1. register1 = counter (Đọc giá trị từ RAM vào thanh ghi)
  2. register1 = register1 + 1 (Tăng giá trị thanh ghi)
  3. counter = register1 (Ghi lại giá trị từ thanh ghi vào RAM)

Nếu $P_1$ đang chạy bước 1 và 2 thì bị ngắt, $P_2$ nhảy vào chạy cả 3 bước, sau đó $P_1$ được cấp CPU chạy nốt bước 3 $\rightarrow$ Giá trị counter cuối cùng sẽ là $6$ thay vì $7$! Dữ liệu bị sai hỏng hoàn toàn.

B. Vùng Tranh Chấp (Critical Section - CS)

Critical Section là đoạn mã nguồn của tiến trình mà trong đó tiến trình truy xuất và thay đổi dữ liệu dùng chung.

C. 3 Yêu cầu Bắt buộc cho Giải pháp CS

  1. Loại trừ tương hỗ (Mutual Exclusion): Nếu tiến trình $P_i$ đang thực thi trong vùng CS của nó, thì không có tiến trình $P_j$ nào khác được phép thực thi trong vùng CS đó.
  2. Tiến triển (Progress): Nếu không có tiến trình nào đang ở trong vùng CS và có các tiến trình muốn vào CS, thì chỉ những tiến trình không nằm trong Remainder section mới được tham gia quyết định tiến trình tiếp theo được vào CS, và sự lựa chọn này không thể kéo dài vô hạn.
  3. Chờ đợi giới hạn (Bounded Waiting): Có một giới hạn về số lần các tiến trình khác được phép vào vùng CS của chúng sau khi một tiến trình đã đưa ra yêu cầu vào CS và trước khi yêu cầu đó được chấp nhận (Đảm bảo không tiến trình nào bị đói tài nguyên / Starvation).

2. GIẢI PHÁP ĐỒNG BỘ: THUẬT TOÁN PETERSON VÀ SEMAPHORE

A. Thuật toán Peterson cho 2 Tiến trình

Giải pháp phần mềm cổ điển cho 2 tiến trình $P_0$ và $P_1$ chia sẻ 2 biến:

int turn;
boolean flag[2]; // ban đầu khởi tạo false

// Cấu trúc tiến trình Pi (i = 0 hoặc 1, j = 1 - i)
while (true) {
    flag[i] = true;
    turn = j;
    while (flag[j] && turn == j) ; // Busy waiting
    
    /* CRITICAL SECTION */
    
    flag[i] = false;
    
    /* REMAINDER SECTION */
}

Thuật toán Peterson chứng minh thỏa mãn cả 3 điều kiện: Mutual Exclusion, Progress và Bounded Waiting.

B. Semaphore

Semaphore $S$ là một biến nguyên tử (Atomic integer) chỉ có thể truy xuất thông qua 2 thao tác nguyên tử chuẩn:

⚙️ ĐỊNH NGHĨA NGUYÊN TỬ CỦA SEMAPHORE

Thao tác wait(S) (hoặc P(S) / sem_wait(&S)):

void wait(Semaphore S) {
    S.value--;
    if (S.value < 0) {
        // Thêm tiến trình này vào hàng đợi của Semaphore S
        block(); // Chuyển tiến trình sang trạng thái Waiting
    }
}

Thao tác signal(S) (hoặc V(S) / sem_post(&S)):

void signal(Semaphore S) {
    S.value++;
    if (S.value <= 0) {
        // Lấy một tiến trình P từ hàng đợi của Semaphore S
        wakeup(P); // Chuyển tiến trình P sang trạng thái Ready
    }
}
⚠️ ĐỪNG NHẦM: Counting Semaphore vs Binary Semaphore
  • Counting Semaphore: Giá trị có thể dao động không hạn chế. Dùng để quản lý số lượng thực thể của một tài nguyên hữu hạn.
  • Binary Semaphore: Giá trị chỉ có thể là $0$ hoặc $1$. Hoạt động tương tự Mutex Lock nhưng không có tính sở hữu (Ownership). Dùng làm khóa truy xuất độc quyền hoặc đồng bộ thứ tự.

C. Đồng Bộ Phần Cứng (Hardware Instructions: TestAndSet & Swap)

Các bộ xử lý hiện đại cung cấp các chỉ thị máy nguyên tử (Atomic hardware instructions) executed không thể bị ngắt giữa chừng:

// 1. Chỉ thị TestAndSet nguyên tử
boolean TestAndSet(boolean *target) {
    boolean rv = *target;
    *target = true;
    return rv;
}

// Giải pháp CS dùng TestAndSet:
while (TestAndSet(&lock)) ; // Busy wait
/* CRITICAL SECTION */
lock = false;

D. Giám Sát Viên (Monitor) & Biến Điều Kiện (Condition Variables)

Semaphore tuy mạnh mẽ nhưng dễ gây ra lỗi lập trình (như quên signal hoặc đảo vị trí wait gây Deadlock). Monitor (Giám sát viên) là một cấu trúc ngôn ngữ lập trình bậc cao tự động đảm bảo tính Loại trừ tương hỗ (Mutual Exclusion): tại một thời điểm chỉ có ĐÚNG MỘT tiến trình được thực thi mã bên trong Monitor.

  • Biến điều kiện (Condition Variable): Khai báo condition x, y; để cho phép tiến trình tạm dừng bên trong Monitor.
  • x.wait(): Tiến trình gọi lệnh này sẽ bị treo và giải phóng Monitor cho tiến trình khác vào.
  • x.signal(): Đánh thức ĐÚNG MỘT tiến trình đang chờ trên x.wait(). Nếu không có tiến trình nào chờ, lệnh `signal` bị trôi mất (không có bộ đệm lưu trữ như Semaphore!).
  • Hoare vs Mesa Semantics: Signal-and-Wait (Hoare) cho tiến trình được đánh thức chạy ngay lập tức; Signal-and-Continue (Mesa) cho tiến trình phát `signal` tiếp tục chạy hết Monitor rồi tiến trình được đánh thức mới chạy.

E. Hàng Rào Bộ Nhớ (Memory Barrier / Memory Fence)

Trên các kiến trúc đa luồng và đa lõi hiện đại, trình biên dịch và phần cứng CPU có thể tự động đổi thứ tự thực thi lệnh (Instruction Reordering) nhằm tối ưu hóa hiệu năng đường ống (Instruction Pipeline). Điều này có thể khiến các luồng khác nhìn thấy thứ tự cập nhật dữ liệu bộ nhớ không đúng.

Hàng rào bộ nhớ (Memory Barrier / Memory Fence) là một chỉ thị phần cứng buộc hệ thống phải hoàn tất tất cả các thao tác nạp (Load) và lưu (Store) trước đó vào bộ nhớ trước khi thực thi bất kỳ thao tác bộ nhớ nào sau hàng rào, bảo đảm tính nhất quán dữ liệu trong lập trình đồng thời cấp thấp.

3. CÁC BÀI TOÁN ĐỒNG BỘ KINH ĐIỂN VÀ BÀI TẬP CHUẨN THI UIT

A. 3 Bài Toán Đồng Bộ Kinh Điển

📦 1. BÀI TOÁN NHÀ SẢN XUẤT - NGƯỜI TIÊU THỤ (PRODUCER - CONSUMER)

Bộ đệm chia sẻ gồm $N$ phần tử. Producer tạo dữ liệu đưa vào buffer, Consumer lấy dữ liệu ra khỏi buffer.

semaphore mutex = 1; // Độc quyền truy xuất Buffer
semaphore empty = N; // Đếm số ô trống
semaphore full = 0;  // Đếm số ô có dữ liệu

// Producer
do {
    produce_item();
    wait(empty); wait(mutex);
    append_buffer();
    signal(mutex); signal(full);
} while (true);

// Consumer
do {
    wait(full); wait(mutex);
    take_buffer();
    signal(mutex); signal(empty);
    consume_item();
} while (true);
📚 2. BÀI TOÁN BẠN ĐỌC - NGUỜI VIẾT (READERS - WRITERS)

Nhiều tiến trình chia sẻ dữ liệu. Nhiều Reader có thể đọc đồng thời; nhưng khi Writer ghi dữ liệu, phải độc quyền hoàn toàn (không ai khác được đọc/ghi).

semaphore rw_mutex = 1; // Độc quyền cho Writer
semaphore mutex = 1;    // Bảo vệ biến read_count
int read_count = 0;

// Reader
wait(mutex);
read_count++;
if (read_count == 1) wait(rw_mutex); // Reader đầu tiên khóa Writer
signal(mutex);

/* READING DATABASE */

wait(mutex);
read_count--;
if (read_count == 0) signal(rw_mutex); // Reader cuối cùng mở khóa Writer
signal(mutex);

// Writer
wait(rw_mutex);
/* WRITING DATABASE */
signal(rw_mutex);
🍜 3. BÀI TOÁN BỮA ĂN CỦA CÁC TRIẾT GIA (DINING PHILOSOPHERS)

5 Triết gia ngồi quanh bàn tròn, giữa mỗi cặp triết gia có 1 chiếc đũa (tổng 5 đũa). Để ăn, triết gia cần 2 đũa bên trái và bên phải.

Nguy cơ Deadlock: Nếu tất cả 5 triết gia cùng nhặt đũa bên trái cùng lúc $\rightarrow$ Không ai nhặt được đũa bên phải $\rightarrow$ Deadlock!

Giải pháp khắc phục: Cho phép tối đa 4 triết gia ngồi ăn cùng lúc; hoặc triết gia chỉ nhặt đũa khi cả 2 đũa trái/phải đều sẵn sàng (dùng Monitor / Semaphore asymmetric).

B. Bài Tập Đồng Bộ Sơ Đồ Phụ Thuộc (DAG) Chuẩn Thi UIT

📝 WORKED EXAMPLE 1: ĐỒNG BỘ SƠ ĐỒ TIẾN TRÌNH BẰNG SEMAPHORE
Bài toán: Xét một hệ thống gồm 4 tiến trình $T_1, T_2, T_3, T_4$. Quan hệ phụ thuộc được mô tả: $T_1$ phải kết thúc trước khi $T_2$ và $T_3$ bắt đầu. Cả $T_2$ và $T_3$ phải kết thúc trước khi $T_4$ bắt đầu. Hãy khai báo Semaphore và viết mã đồng bộ cho 4 tiến trình trên.
Lời giải chi tiết từng bước:
  1. Phân tích quan hệ phụ thuộc (DAG):
    - $T_1 \rightarrow T_2$ và $T_1 \rightarrow T_3$ (Cần tín hiệu từ $T_1$).
    - $T_2 \rightarrow T_4$ và $T_3 \rightarrow T_4$ ($T_4$ cần chờ cả $T_2$ và $T_3$).
  2. Khai báo và Khởi tạo Semaphore: 
    semaphore sem1 = 0; // Báo hiệu T1 đã hoàn thành
semaphore sem2 = 0; // Báo hiệu T2/T3 đã hoàn thành
  3. Viết mã nguồn cho các tiến trình: 
    void T1() {
    // T1 thực thi công việc
    signal(sem1); // Gửi tín hiệu cho T2
    signal(sem1); // Gửi tín hiệu cho T3
}

void T2() {
    wait(sem1);   // Chờ T1 xong
    // T2 thực thi công việc
    signal(sem2); // Gửi tín hiệu cho T4
}

void T3() {
    wait(sem1);   // Chờ T1 xong
    // T3 thực thi công việc
    signal(sem2); // Gửi tín hiệu cho T4
}

void T4() {
    wait(sem2);   // Chờ T2 xong
    wait(sem2);   // Chờ T3 xong
    // T4 thực thi công việc
}
📝 WORKED EXAMPLE 2: SỬA LỖI BIẾN X VƯỢT QUÁ 20
Cho đoạn code C chia sẻ biến X giữa 2 tiến trình: 
do {
    X = X + 1;
    if (X == 20) X = 0;
} while (TRUE);
Hãy giải thích nguyên nhân làm $X > 20$ và dùng Semaphore để sửa lỗi.
Lời giải:

Nguyên nhân: Race condition giữa bước tăng $X$ và bước kiểm tra if (X == 20). Nếu $X = 19$, $P_1$ tăng $X$ thành $20$ nhưng bị ngắt trước if. $P_2$ nhảy vào tăng $X$ thành $21$. Khi $P_1$ chạy tiếp if (X == 20) $\rightarrow$ sai (vì $X = 21$) $\rightarrow X$ không về $0$ và tiếp tục tăng lên $22, 23...$

Khắc phục bằng Semaphore: Bọc toàn bộ đoạn tăng và kiểm tra trong Mutex Semaphore mutex = 1.

semaphore mutex = 1;
do {
    wait(mutex);
    X = X + 1;
    if (X == 20) X = 0;
    signal(mutex);
} while (TRUE);
📌 Quick Recall Chương 5
  • 3 Yêu cầu CS: Mutual Exclusion, Progress, Bounded Waiting.
  • wait(S) giảm S (kẹt nếu $S \le 0$), signal(S) tăng S (đánh thức tiến trình chờ).
  • Monitor tự động khóa Mutual Exclusion, dùng condition x; x.wait(), x.signal().
  • Producer-Consumer: empty=N, full=0, mutex=1.
  • Khởi tạo Semaphore $= 0$ cho đồng bộ thứ tự (DAG), $= 1$ cho độc quyền truy xuất (CS).
